# 가상 사례 — 개인 PBL 작성 예시

> 교육용 **가상** 데이터입니다. 실제 결과가 아니며 그대로 제출하지 않습니다. (가상 팀원 B, WBS-04)

| 절 | 작성 예 |
|---|---|
| Problem | 동일 ID로 가입하면 거부되어야 하는데 일부 요청이 통과된다. 완료 기준: 동시 요청 포함 TC-02 10회 모두 거부 |
| Facts | 순차 요청 5/5 거부(로그 URL). 동시 요청 5회 중 2회 중복 저장됨(DB 캡처 URL) |
| 가설 | (가설) 애플리케이션 코드에서만 중복을 검사하고 DB에는 고유 제약이 없다 → 테이블 스키마 확인으로 검증 |
| Ideas | A: 코드 검사 강화(장점: 빠름 / 단점: 동시성 문제 남음) · B: DB 고유 제약 추가(장점: 근본 해결 / 단점: 기존 중복 데이터 정리 필요) → **B 선택** |
| Learning | DB 고유 제약과 트랜잭션 격리 수준 조사(자료 링크) |
| Action | 10/20 14:00–16:00 스키마 확인(2h) · 10/21 고유 제약 추가 커밋(커밋 URL) · 중복 데이터 정리 스크립트 작성 |
| Result | 정상: 신규 ID 가입 성공 / 오류: 중복 ID 동시 10회 → 10/10 거부 / 개선 전 3/5 → 개선 후 10/10 |
| Reflection | 코드만 보고 “완료”라고 판단했던 것이 문제. 데이터 무결성은 DB에서도 보장해야 한다 |
| 협업 근거 | 팀원 A가 동시 요청 시험 스크립트를 리뷰해 줌(PR 코멘트 URL) |
| 자원관리 근거 | 계획 3h, 실제 5h. 스키마 조사 시간을 과소추정 → 다음 주 계획에 반영 |
